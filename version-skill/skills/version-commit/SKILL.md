# 版本提交

## 检查仓库

- 仓库范围：只处理用户指定的 Git 仓库；多个仓库分别检查、形成方案和记录结果。
- 仓库证据：读取足以判断当前分支、改动内容、提交状态和远程关系的仓库证据。
- 提交条件：确认仓库能够创建普通提交；存在会改变提交语义或需要先完成的仓库操作时，停止处理该仓库并说明原因。
- 仓库约定：读取适用于当前仓库的协作说明和近期提交记录，确定提交粒度与提交信息风格。
- 空改动：仓库没有可提交改动时，说明当前状态并跳过该仓库。

## 形成提交方案

- 提交边界：根据改动目的和依赖关系划分提交，使每个提交形成可独立说明的版本变化；无法可靠判断改动归属时交由用户确认。
- 提交信息：根据实际改动和仓库约定形成能够准确概括版本变化的推荐提交信息。
- 远程动作：确认本地分支、远程目标和推送关系；没有适用的远程仓库时，将远程创建和关联列入待确认动作。
- 提交预演：按 `$discuss-execution` 将每个逻辑提交作为独立预演项，说明仓库、改动范围、推荐提交信息以及本地和远程动作；以用户最终批准的方案作为执行依据。

## 创建本地提交

- 状态复核：执行前重新读取仓库状态；当前状态与批准方案不一致时，更新提交方案并重新取得批准。
- 暂存与提交：按批准的提交边界暂存改动并使用批准的提交信息创建本地提交，保留范围外改动的当前状态。
- 失败处理：本地提交失败时停止当前方案，不执行对应的远程动作，并说明失败状态。

## 同步远程仓库

- 已有远程：按批准的远程和分支关系执行普通推送，并在需要时建立当前分支的上游关系。
- 创建远程：没有适用的远程仓库时询问用户是否创建；用户同意后确认托管平台、仓库归属、名称和可见性，使用对应平台的命令行创建并关联远程仓库，例如 GitHub 使用 `gh`。
- 推送受阻：普通推送无法完成时保留本地提交，说明阻碍，并将需要同步历史或改变远程状态的处理作为新的待确认动作。

## 确认结果

- 独立处理：各提交方案独立执行和记录；某项失败后，只继续不依赖该项且仍获批准的其他方案。
- 结果汇总：分别说明各仓库的提交标识、提交信息、所在分支、远程同步结果和剩余改动。
