# Note JetBrains Code

## 概述

把 JetBrains IDE 作为学习库的首要证据源。先确认 IDE 和工程上下文、询问库名，再在 IDE 中定位库、统计 API，并按批次讲解；每批结束后先等用户反馈，再继续。

## 主流程

1. 确认 JetBrains 上下文。
2. 询问目标库。
3. 在 IDE 中定位库。
4. 扫描并统计 API。
5. 让用户选择学习范围。
6. 分批教学并等待反馈。

## 确认 JetBrains 上下文

- 检查是否存在可用的 JetBrains MCP，以及它当前连接的 IDE 和工程。
- 能映射时优先按语言匹配 IDE：
  `GoLand -> Go`，`IntelliJ IDEA -> Java/Kotlin`，`PyCharm -> Python`，`WebStorm -> JavaScript/TypeScript`，`RustRover -> Rust`，`CLion -> C/C++`。
- 先尝试连接，再明确说明能做到什么、做不到什么；不要一开始就承诺一定能做到。
- 把 JetBrains IDE 作为主证据源，不要把网页 API 搜索作为主流程。

## 先问最少但必要的问题

- 第一问只问用户要学习的库名。
- 仅在库名存在歧义、当前有多个 JetBrains MCP 可选，或用户没有给出足够语言线索时，才补问语言或 IDE。
- 如果用户已经给出明确的包名、模块名、命名空间或类名，不要重复追问。

## 在 IDE 中定位库

按下面的顺序定位，拿到可靠入口后停止继续扩搜：

1. 确认当前工程是否已经依赖这个库。
2. 搜索依赖文件、导入语句、全限定名、调用点、类型引用、常量引用。
3. 优先选择公开符号和真实使用点，不要先钻进随机内部文件。
4. 从使用点跳到符号声明、文档、声明文件和声明位置。
5. 确认该库是标准库还是第三方库。

优先使用的线索：

- 依赖文件，例如 `go.mod`、`pom.xml`、`build.gradle`、`requirements.txt`、`package.json` 或等价文件。
- 工程里已经存在的导入语句或包引用。
- 代表性的函数调用、方法调用、构造器调用、类型使用、常量使用。
- IDE 的符号搜索、文本搜索、声明跳转和符号说明能力。

如果当前工程里没有这个库：

- 明确告诉用户，当前 IDE 上下文还不足以暴露这个库。
- 让用户切换到已经依赖该库的工程。
- 只有在具备写权限且用户明确同意时，才考虑创建临时 probe 文件去导入或引用该库。

如果 IDE 对外部源码全文读取有限制，但符号解析仍然可用：

- 继续使用符号说明、声明文本、声明路径、调用点、示例和测试来教学。
- 明确区分“已验证的信息”和“根据签名/调用点推断的信息”。

## 版本提醒

- 开始教学前，先尽量确认当前学习上下文的库版本或 SDK 版本。
- 标准库要区分工程声明版本和实际 SDK 版本；如果两者不一致，要一起告诉用户。
- 如果能可靠确认当前版本不是最新版，要先提醒用户当前学习基于旧版本。
- 如果不能可靠确认最新版，就只说明当前已验证版本，不要猜测“最新”。

## 先统计再提学习选项

在让用户选择学习范围之前，先完成扫描并给出：

- `常用 API: N`
- `全部 API: M`
- `当前学习版本: V`（如果可验证）

默认约定：

- `全部 API` 指当前 IDE 上下文中可发现的全部公开 API。
- 除非用户明确要求，否则不要把私有实现、内部辅助函数、未导出成员算进去。
- `常用 API` 是推荐的第一批学习集合，属于启发式结果，不是绝对真理。

如果因为 IDE 能力或索引限制无法精确统计：

- 给出当前能验证到的最好数量，并明确标注这是近似值。
- 说明哪些类别没有办法精确统计。

## 如何判断“常用 API”

优先把以下内容纳入 `常用 API`：

- 包、模块或类文档中直接提到的主入口。
- 构造器、工厂函数、初始化入口。
- 核心类型上的关键方法。
- 工程、示例或测试里反复出现的 API。
- 能形成一条典型 happy path 的 API 组合。

默认不要把以下内容放进第一批：

- 已废弃 API。
- 兼容层、胶水层、过于底层的 API。
- 看起来更像内部实现细节的公开符号。

## 让用户选择学习范围

给出数量后，让用户在 `常用 API` 和 `全部 API` 之间选择；如果用户没有明确选择，默认从 `常用 API` 开始。

## 分批教学

- 默认每批讲 `6-10` 个 API，或者一组强相关的类型簇。
- 不要机械按字母顺序输出，优先按概念关系或调用流程分组。
- 如果内容很多，先告诉用户这会分多轮完成。
- 每讲完一批就停下来，询问用户这一批是否有不懂的地方，是否继续下一批；只有在用户表示已经理解，或者明确说“继续”之后，才进入下一批。
- 如果用户不理解，就停在当前批次，换一种更简单的说法，必要时补一个案例，再继续解释。

组织每一批内容时：

- 最终输出使用该语言习惯的术语，但扫描时可先按包/模块、函数、方法、构造器或工厂、类型、变量或常量这些通用类别组织。
- 讲解函数、方法、构造器或工厂时，默认附一行便于记笔记的简签名。
- 不同 API 类型的讲解要点、语言术语映射、笔记签名写法，以及何时必须补案例，见 [references/teaching-notes.md](references/teaching-notes.md)。

## 质量要求

- 把 JetBrains 的符号说明、声明文本、本地文档、示例和测试作为首要证据。
- 优先讲公开 API，不要把深层内部实现当作学习主线。
- 如果 IDE 能看到废弃标记、实验标记或 warning，要明确告诉用户。
- 不要编造 API、数量、说明或行为。

## 失败处理

- 如果没有可用的 JetBrains MCP，明确说明当前无法走本地 IDE 学习流程。
- 如果 IDE 或工程不对，明确告诉用户应该打开什么类型的工程。
- 如果当前工程没有依赖目标库，引导用户切换到正确工程，或者在获得同意后创建临时 probe 文件。
- 如果只能拿到部分信息，就继续讲已验证部分，并把缺失项说清楚。
